# Кнессет-Трекер

Гражданская платформа над официальными данными Кнессета: отслеживание законопроектов,
профили депутатов, реакции и обсуждения, гражданские законодательные инициативы
и многоязычный AI-анализ каждого законопроекта.

## Что уже работает

- **Данные Кнессета.** Инкрементальная синхронизация с OData API Кнессета
  (законопроекты, депутаты, фракции, инициаторы, фото) фоновым сервисом каждые 6 часов.
- **Законопроекты.** Список с поиском и фильтрами, карточка закона, бейдж «окно влияния» —
  на какой стадии на закон ещё можно повлиять, а когда уже поздно.
- **Реакции и обсуждение.** Трёхцветный бар «за / не определился / против» с честным показом
  размера выборки, комментарии с тегами типа аргумента.
- **Гражданские инициативы.** Черновик → публикация → сбор подписей → порог.
  Явно помечены как **не официальные законопроекты**.
- **AI-анализ.** Мастер-анализ генерируется на английском, затем лениво переводится на все
  поддерживаемые языки; вся история версий сохраняется и показывается.
  Правила симметрии для любой модели зафиксированы в
  [`src/Kneset.Core/Ai/analysis-policy.md`](src/Kneset.Core/Ai/analysis-policy.md).
- **Локализация.** he / ar / ru / en, RTL для иврита и арабского. Тексты интерфейса живут
  в таблице `UiTranslations` с фолбэком на `.resx`.
- **Шеринг.** Ссылки в WhatsApp / Telegram / X, якоря на конкретные комментарии и
  динамические OG-превью, которые рисуются под каждый закон и инициативу.

## Стек

.NET 10 · Blazor Server (Interactive Server) · модульный монолит ·
EF Core + PostgreSQL (Supabase) · ASP.NET Identity · SixLabors.ImageSharp

```
src/Kneset.Core            сущности, интерфейсы, политика AI-анализа
src/Kneset.Infrastructure  EF Core, клиенты Кнессета, реализации AI-провайдеров
src/Kneset.Web             Blazor-приложение, фоновые сервисы, эндпоинты OG-картинок
```

## Запуск

Нужен .NET 10 SDK и база PostgreSQL (проект разрабатывался на Supabase).

1. Строка подключения — в user-secrets, в репозиторий она не попадает:

```bash
dotnet user-secrets set "ConnectionStrings:Default" "Host=...;Database=postgres;Username=...;Password=..." --project src/Kneset.Web
```

2. Применить миграции и запустить:

```bash
dotnet ef database update --project src/Kneset.Infrastructure --startup-project src/Kneset.Web
```

```bash
dotnet run --project src/Kneset.Web
```

Первый старт синхронизирует данные Кнессета — это занимает несколько минут.
Отключить синхронизацию можно флагом `Sync:Enabled=false`.

## Деплой на Render

Render не поддерживает .NET нативно (только Node, Python, Ruby, Go, Rust и Elixir),
поэтому сборка идёт через [`Dockerfile`](Dockerfile). В дашборде нужен тип сервиса
**Web Service** — приложению нужен постоянно работающий процесс с WebSocket-соединениями.
Параметры описаны в [`render.yaml`](render.yaml), Render подхватит его как Blueprint.

Единственная переменная окружения, которую нужно задать руками, — строка подключения:

```
ConnectionStrings__Default=Host=...;Database=postgres;Username=...;Password=...
```

Двойное подчёркивание — это разделитель уровней конфигурации в .NET, оно обязательно.

Важные ограничения:

- **Только один инстанс.** Blazor Server держит состояние страницы в SignalR-цепи на
  конкретном инстансе, а балансировщик Render распределяет запросы равномерно и не
  закрепляет сессию. При двух инстансах страницы будут произвольно рвать соединение.
- **Не free-тариф.** Бесплатный сервис засыпает после 15 минут без трафика, а вместе с ним
  умирает фоновая синхронизация с Кнессетом и очереди AI-анализа.
- **Миграции не применяются автоматически.** После деплоя, меняющего схему, выполните
  `dotnet ef database update` с локальной машины против той же базы.

## AI-провайдер

Сейчас включён `Ai:Provider=Stub` — все три интерфейса (`IBillAnalyzer`,
`IAnalysisTranslator`, `IInitiativeDrafter`) отдают демо-данные без обращения к внешнему API.
Подключение реальной модели — это один класс-провайдер на интерфейс и смена значения флага;
трогать остальной код не нужно.
